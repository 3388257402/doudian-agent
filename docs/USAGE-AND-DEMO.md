# 怎么用 · 怎么讲（使用手册 + 演示脚本）

> 这一份解决两个问题：**你自己怎么跑起来**，以及**你怎么在三分钟内给别人讲明白**。
> 所有命令都在本机实跑过（见文末「验证记录」）。

---

# 第一部分：怎么用

## 一句话说清它是什么

运营每天要盯 GMV、退款率、库存，发现了问题还得手动改价/补货，改完没人知道效果。
这个系统把这条链路串成一条**可审计的流水线**：

```
拉数据 → 算指标 → 按规则判异常 → （模型写一句人话解释）→ 提动作 → 人工审批 → 执行 → T+1 回看效果
```

**关键约束：涉钱的动作必须人点头；模型只解释，不决策。**

## 三种使用方式

### 方式 A：零凭据跑通（自己验证 / 给别人看效果）

```powershell
# 1) 后端
.\.venv\Scripts\python.exe -m uvicorn app.main:app --app-dir backend --port 8000
#    自检：curl.exe http://127.0.0.1:8000/api/healthz
#    → {"status":"ok","db":"ok","checkpointer":"ok",...}

# 2) 一条命令跑完整流程（不需要任何 API key、不连真店铺）
.\.venv\Scripts\python.exe backend\tests\fixtures\demo\run_demo.py

# 3) 前端
cd frontend; npm install; npm run dev     # → http://localhost:5173
```

**为什么这个顺序**：先跑后端（前端要连它）→ 再跑 demo（灌入真实形状的数据）→ 最后开前端（有数据可看）。
反过来做会发现前端一片空白，容易误判成"前端坏了"。

### 方式 B：只看演示（给对方看，不动代码）

打开 `http://localhost:5173`，三个页面按**这个顺序**看：

| 顺序 | 页面 | 你要让对方注意什么 |
|---|---|---|
| 1 | **看板** | 缺数据的那天**不补零**（缺口就是缺口）；毛利率为 `null` 的天会明确显示"未配置成本" |
| 2 | **审批** | 每条动作都有"为什要改"的依据；通过/驳回都留痕，驳回不会写执行日志 |
| 3 | **日志** | 每一步都有一条 `node.trace`（谁、花了多久、输入输出指纹、成败） |

### 方式 C：接真实店铺（会真的改价，谨慎）

1. 复制 `.env.example` → `.env`，填 `DOUDIAN_APP_KEY / APP_SECRET / ACCESS_TOKEN`
2. 改 `backend/config/settings.yaml`：`doudian.dry_run: false`
3. 先只开价格调整，库存先观察一周

> ⚠️ **这一步会真的改线上价格。** 建议第一周把 `rules.yaml` 里的阈值收紧（宁可漏报，不要误改）。

# 第二部分：怎么讲

## 30 秒电梯版（任何人都能听懂）

> 运营每天手工盯数据、手工改价，改完也不知道有没有用。
> 我做了个系统：它每天自动算出异常、给出要改的动作，**但改之前必须人点通过**；
> 改完过几天再回来看效果。全程有日志，谁改的、为什么改、改了之后怎么样，都能查。

## 3 分钟技术版（五句话 + 每句的证据）

| # | 讲什么 | 证据在哪 |
|---|---|---|
| 1 | **流程是状态机，不是脚本**：9 个节点，审批中断时整个 run 挂起，进程重启后能接着跑 | `backend/app/agent/graph.py`；日志里 `node.trace` 10 条（9 节点 + 审批重放） |
| 2 | **模型在场但不掌权**：它只把异常翻译成一句人话，输出要过 schema 校验，失败就降级 | `llm.skipped` / `llm.degraded` 事件；`backend/app/services/llm.py` |
| 3 | **脏数据不打死整轮**：逐行拒绝并留审计，行账恒等式 `rows_seen = accepted + rejected + out_of_window` | `collect.row_rejected`；测试里是显式 `AssertionError` |
| 4 | **指标口径写死在契约里**：缺数据不补零、未配置成本时毛利率是 `null` 而不是 `0` | `docs/CONTRACT.md` §12；前端不自算，直接显示后端值 |
| 5 | **能证明它跑过**：350 条测试、一条命令零凭据跑完整流程、`demo` 可复现 | `pytest` 全绿；`run_demo.py` 退出码 0 |

## 2 分钟非技术版（讲痛点，不讲技术）

> 你们现在怎么处理"昨天退款率突然 30%"这种事的？
> 一般是有人看到了，去问、去查、去改，改完过几天再看。
> 我这套东西就是把这三步固定下来：**发现**（规则，不是模型猜）→ **确认**（人点通过）→ **回看**（T+1 自动对比效果）。
> 好处是：不会有人"顺手改了一下"但没人知道；也不会有"改了但没效果还在改"。

## 演示动线（现场按这个顺序点，别乱跳）

1. **先看板**（30 秒）：指出"这一天没有数据，这里是空的，不是 0" —— 这一句最容易被记住
2. **再审批**（60 秒）：随便点开一条，念出"它为什么建议改价"，然后点**驳回**（演示留痕）
3. **再看日志**（60 秒）：找到刚才那条驳回，指出"这里有一条记录，包含谁、什么时候、依据是什么"
4. **最后讲一句架构**（30 秒）：只讲"人审批这一环不能省"

## 五个必问问题 + 回答

| 对方可能问 | 你怎么答 |
|---|---|
| "这跟 Dify/Coze 搭的有啥区别？" | 平台擅长"一个人用"；这套是**多步有状态 + 中断可恢复 + 每步可审计**，涉钱流程需要这个 |
| "模型会不会乱改价？" | 不会。动作由 `rules.yaml` 白名单规则产出，模型只写解释；没配 key 时整条链路照跑（`llm.skipped`） |
| "挂起了没人审批怎么办？" | 一直挂着，不自动过期（这是**故意**的：自动执行才是事故） |
| "数据错了会怎样？" | 逐行拒绝并记录原因，整轮照跑；不会因为一行坏数据全批失败 |
| "怎么证明它有效？" | T+1 回看：把执行后的指标和基线对比，`effect_report` 里能查到 |

## 讲的时候**不要**做的三件事

| 别说 | 为什么 |
|---|---|
| "AI 自动改价" | 事实是**规则决策 + 人审批**。说错一次，后面全被怀疑 |
| "支持多店铺/权限/告警" | 没做就没做（README 明写"未做"）。被追问一句就露 |
| "这个能直接上生产" | 它是**原型**：单店铺、无线程池压测、无告警。老实说反而加分 |
